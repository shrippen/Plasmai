# Release steps

In this order, from the version bump to done. Commands and background per target: `RELEASING.md`.

1. Version `X.Y.Z` (on a branch `release/X.Y.Z`) in `metadata.json`, `app/CMakeLists.txt` (`project`, `QT_ANDROID_VERSION_NAME`, `QT_ANDROID_VERSION_CODE` = major·10000 + minor·100 + patch), `app/android/AndroidManifest.xml` (`versionName`, `versionCode`), `app/main.cpp` (`kAppVersion`), `STORE.md`, `translate/extract.sh` and `translate/template.pot` (package version), a `<release>` in `packaging/linux/io.github.shrippen.Plasmai.metainfo.xml` and `fastlane/metadata/android/{en-US,de-DE}/changelogs/<versionCode>.txt`; then `scripts/bump-build.sh` (`build.number`, `contents/code/buildInfo.js`).
2. Release log in `CHANGELOG.md`, before the tag: a section `## [X.Y.Z] — YYYY-MM-DD` below `## [Unreleased]` (newest first), with `### English` and `### Deutsch`, each a lead (what the release is about, one or two sentences), then the groups New, Improved, Fixed and Note (Neu, Verbessert, Behoben, Hinweis; breaking changes, steps the user must take) as `####`. Empty groups are left out. Each point says what changed for the user and why, not which code moved. The English part ends with `All changes: https://github.com/shrippen/Plasmai/compare/vA...vB`. Check with `scripts/release-notes.sh --check` (CI runs it on every push) and read the notes with `scripts/release-notes.sh X.Y.Z`.
3. Landing page `docs/index.html`: the same text as a new entry at the top of `#changes` (Kante `.changelog`, both languages, compare link); from the fourth entry on, the oldest move into `details.changelog-more`. Bump the version in the footer. Graphics: a screenshot from the demo world per visible change (`demo/shots.json`, `../shrippen.github.io/demo/tools/.venv/bin/python ../shrippen.github.io/demo/tools/screenshots.py plasmai`, saved as `docs/shots/release-X.Y.Z-<name>-<lang>.webp`), a diagram for changes inside. Screenshots are taken only now, for a tagged release.
4. PR with steps 1–3, review as the skill `pr-review` says; the owner confirms the release in words (it publishes); CI green; merge on Gitea.
5. Tag the merge commit and push the tag to Gitea only (the mirror carries it to GitHub): `git tag -a vX.Y.Z -m "X.Y.Z" <merge commit> && git push origin vX.Y.Z`.
6. Gitea release, notes only, no files: `scripts/release-notes.sh X.Y.Z > notes.md && gt release create vX.Y.Z --repo shrippen/plasmai --title "Plasmai X.Y.Z" --notes-file notes.md --no-input`.
7. GitHub: the tag starts `.github/workflows/release.yml`, which creates the release with the same notes (`scripts/release-notes.sh`; it fails without the section) and attaches `Plasmai-X.Y.Z.apk` (signed), `.AppImage`, `.flatpak`, `.plasmoid`, `-setup.exe`, `-windows-x64.zip` and `install-linux.sh`. Check the run (`gh run list -R shrippen/Plasmai -w release.yml`) and that the release has all seven files. A failed job: report it to the owner and stop; a fix goes through a PR (review, merge on Gitea) first, and a new run that attaches files (`gh workflow run release.yml -R shrippen/Plasmai -f tag=vX.Y.Z`) only with the owner's permission in words, because it publishes on GitHub.
8. `python3 ../shrippen.github.io/overview/tools/build-versions.py`, then commit `docs/versions.json` in `shrippen.github.io` via a PR there.
9. KDE Store: upload the `.plasmoid` from the GitHub release to https://store.kde.org/p/2368175/ and update version and changelog there (`STORE.md`). F-Droid and Flathub are prepared but not submitted (`RELEASING.md` 4.6, 5.2).
10. Done when https://shrippen.github.io/Plasmai/ shows the release in `#changes` and the footer, and https://shrippen.github.io/versions.json has it.

The release-notes script is a copy of Kante's `tools/release-notes.sh`: change it only there, then sync with `../Kante/tools/sync-release-notes.sh "$PWD"`.
